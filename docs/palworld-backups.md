# Palworld Backups

GamesHud manages Palworld backups as a temporary personal Palworld integration before the planned plugin system.

Backups are stored as `.tar.gz` archives plus sidecar `.json` metadata in the configured backup directory.

## Configuration

```text
Palworld__ManagedPath=/managed/palworld
Palworld__BackupPath=/managed/palworld-backups
Palworld__ContainerName=palworld-server-example
Palworld__Backups__AutomaticEnabled=false
Palworld__Backups__AutomaticIntervalMinutes=360
Palworld__Backups__RetentionCount=24
Palworld__Backups__RetentionDays=7
Palworld__Backups__PreBackupSaveDelaySeconds=2
Palworld__Backups__LifecycleTimeoutSeconds=30
```

`Palworld__BackupPath` must be separate from `Palworld__ManagedPath`. GamesHud rejects overlapping paths to avoid deleting backup archives during restore.

The client never sends filesystem paths. Backup ids are generated by the backend.

## Endpoints

```text
GET /api/palworld/backups
GET /api/palworld/backups/{backupId}
GET /api/palworld/backups/{backupId}/download
POST /api/palworld/backups
POST /api/palworld/backups/{backupId}/restore
DELETE /api/palworld/backups/{backupId}
```

## Backup Metadata

Each backup exposes:

- `id`
- `createdAt`
- `sizeBytes`
- `filename`
- `status`
- `type`
- `note`
- `worldSaveStatus`
- `downloadUrl`

Backup types:

- `manual`
- `automatic`
- `pre-restore`
- `pre-update`

## Create Backup

Manual and automatic backup creation use an online flow:

1. Ask the Palworld REST API to save the world through `POST /v1/api/save` when REST is configured.
2. Wait `Palworld__Backups__PreBackupSaveDelaySeconds`.
3. Create a `.tar.gz` archive from `Palworld__ManagedPath`.
4. Write sidecar metadata.
5. Apply automatic-backup retention.

If the REST API is not configured or the save request fails, GamesHud still creates the backup and records `worldSaveStatus` as `unavailable` or `failed`.

This phase does not stop Palworld for backup creation.

## Restore

Restore is destructive and requires the exact confirmation text:

```text
RESTORE PALWORLD BACKUP
```

Restore flow:

1. Read players online from Palworld REST metrics when available.
2. Stop only the configured Palworld container.
3. Create a `pre-restore` backup.
4. Validate the selected backup archive.
5. Replace the managed directory contents from the selected archive.
6. Start only the configured Palworld container.
7. Check whether the configured container is running and whether REST metrics respond.
8. Return the result to the frontend.

If restore fails after the `pre-restore` backup is created, GamesHud attempts to restore that pre-restore archive.

GamesHud must never stop, start, remove, recreate or modify any other container during this flow.

## Delete

Delete requires the exact confirmation text:

```text
DELETE PALWORLD BACKUP
```

Delete removes the selected archive and its metadata. GamesHud refuses to delete the last valid completed backup.

## Automatic Backups

Automatic backups use an internal `BackgroundService`. Cron is not required in this phase.

Automatic backups are disabled by default. When enabled, they use the configured interval and retention settings.

## Retention

Retention applies to automatic backups.

- Keep the newest automatic backups within `Palworld__Backups__RetentionCount`.
- Remove automatic backups older than `Palworld__Backups__RetentionDays`.
- Never remove the last valid completed backup.
- Manual and `pre-restore` backups are not pruned automatically in this phase.

## Security Notes

- Do not expose the Palworld REST API publicly.
- Do not send REST credentials to the frontend.
- Do not commit real backup paths, container names, VPS addresses, passwords or tokens.
- Do not point `Palworld__BackupPath` at unrelated existing backup archives without reviewing retention behavior.
- Validate restore only on a controlled server and with a known-good backup.
